# Автоматическое обновление КлиентРадара

Подготовлено 04.11.2026 для `abdylzhelil/CRM-bot-tg`, рабочей ветки
`ccr-a042c0a9-cjx9fv`. `main` не используется. Образец Modexa изучен,
но её репозиторий, ключи, контейнеры, база и сети не меняются.

## Состояние подключения

Файлы подготовлены. Автоматика выключена по умолчанию: job запускается,
только если **Repository variable** `CRM_AUTO_DEPLOY_ENABLED` равна `true`.
Разовая настройка сервера и первый настоящий цикл пока не подтверждены.
Не считать зелёные тесты доказательством выкладки на сервер.

## Устройство и проверки

CRM — один Compose-сервис `bot`, Python 3.11, `python -m app.main`.
Данные постоянно хранятся в `./data:/srv/data`. По умолчанию это SQLite WAL
`data/crm.db`; реальное подключение берётся из config работающего контейнера.
`.env` может включать `docker-compose.web.yml` через `COMPOSE_FILE`.
Скрипт сохраняет полностью разрешённую **действующую** конфигурацию Compose,
в том числе местные дополнительные файлы, пути и настройки кабинета.
Конфигурация может содержать секреты: её не выводят в CI или чат.

Кабинет слушает `WEBAPP_PORT` (обычно 8091); `/healthz` проверяет процесс
и доступ к БД. Перед обновлением проверяется старый бот, после — точный ID
нового образа и три успешных ответа подряд. Проверка проходит внутри CRM,
не через Caddy Modexa. Кабинет должен быть включён (`WEBAPP_URL`).
Это не проверка каждого фонового цикла, Telegram, оплат или ИИ — после первого
цикла владелец дополнительно проверяет ответ бота и открытие кабинета.

SQLite: перед сборкой делается согласованная копия через SQLite backup API
при работающем боте. Выполняется `PRAGMA integrity_check`, проверяется наличие
основных таблиц. Копия должна появиться на постоянном диске CRM. Обычное
копирование `.db` при WAL не используется. При PostgreSQL автоматизация
**останавливается** до отдельной настройки нативного дампа и его проверки:
перенос SQLite/PostgreSQL не должен пройти незаметно.

## Порядок выкладки

1. Push рабочей ветки: проходят существующие тесты и SQLite, и PostgreSQL.
   PR и другие ветки не выкладываются. Checkout привязан к `github.sha`.
2. GitHub concurrency `crm-production` и серверный `flock` исключают параллельные
   выкладки CRM. Во время выкладки job не отменяется новым push.
3. Сервер проверяет рабочую ветку, чистоту Git и fast-forward. Местные правки,
   включая неотслеживаемые файлы, не удаляются: обновление останавливается.
   `.env` и `data/` остаются на месте, их Git игнорирует. `reset --hard` нет.
4. Если изменились `models.py`, `migrate.py`, `db.py`, `seed.py`, `dbcopy.py`,
   каталоги миграций или Compose-файлы — нужна отдельная ручная проверка.
   Дополнительно обнаруживаются новые явные SQL DDL в `app/`.
   В CRM схема обновляется при запуске, поэтому одного поиска Alembic недостаточно.
   Нестандартные изменения структуры/данных также должны проходить ручной обзор;
   эвристика DDL не заменяет проверку изменений человеком.
5. Сохраняется предыдущий образ `crm-rollback:<SHA>`, проверенная копия базы,
   закрытые копии `.env`, разрешённого Compose, прежние SHA/ID образа и SHA256 базы.
6. Точный коммит собирается из отдельного `git archive`; старый бот работает.
7. Перед переключением повторно проверяются HEAD ветки на GitHub, местный Git,
   контрольная сумма `.env` и разрешённая конфигурация Compose.
8. Пересоздаётся **только CRM `bot`**, с `--no-deps --no-build`. Существующие
   внешние сети используются как раньше; чужие сервисы не перезапускаются.
9. Если запуск не прошёл — попытка вернуть прежний образ с прежней конфигурацией
   и проверить его. Job остаётся красным даже при успешном возврате.
   Если возврат не удался — явное `ROLLBACK FAILED`, требуется помощь владельца.
10. Только после успешного запуска исходники переходят на проверенный SHA
    через `git merge --ff-only`. Краткий перерыв при смене контейнера возможен.

База автоматически назад **не восстанавливается**: в ней уже могут быть новые
заявки и оплаты. Копии находятся в `data/backups/autodeploy/`, права закрытые;
ежедневная ротация их не удаляет. Их и образы `crm-rollback:*` нужно периодически
архивировать/очищать вручную после проверки работы. Массовый Docker prune не запускается.
Временные разрешённые Compose-файлы удаляются из `.git/crm-autodeploy/` при выходе.

## Разовая настройка — выполнять с сопровождением по одному шагу

1. В Termius проверить ветку, SHA, местные правки, сервис CRM, тип базы и кабинет.
   Никаких `cat .env`, `docker inspect` целиком и снимков секретов.
2. Дождаться зелёных тестов подготовленного коммита. Получить файлы обычным
   `git pull --ff-only` в папке CRM; это **не перезапускает** бота.
   При местных правках сначала сохранить/разобрать их, ничего не сбрасывать.
3. Проверить наличие `gh`; при необходимости установить пакет `gh`.
   Выполнить `gh auth login --hostname github.com --git-protocol https --web`.
   Одноразовый код вводить только на странице GitHub, в чат не отправлять.
   Это временная авторизация настройки; не перенастраивать Git Modexa.
4. В папке CRM выполнить `bash docker/setup-autodeploy.sh`.
   Ввести адрес сервера из Termius и порт (обычно 22).
   Скрипт сначала ставит `CRM_AUTO_DEPLOY_ENABLED=false`, создаёт отдельную
   пару `~/.ssh/crm_actions_ed25519`, добавляет **только новую** строку
   `restrict` в `authorized_keys`, сохраняя остальные, и загружает закрытый ключ
   прямо через `gh secret set`. Ключ нигде не показывается и вручную не копируется.
   Эта SSH-учётная запись имеет Docker-доступ — беречь ключ как доступ к серверу.
5. Проверить независимо работающий `git fetch origin` CRM до выхода из `gh`.
   Если Git зависит от временного gh-входа, сначала настроить отдельный read-only
   доступ CRM; чужие SSH-ключи/настройки не менять. Приватные исходники Modexa не нужны.
6. В GitHub → CRM → Settings → Secrets and variables → Actions проверить имена:
   Secrets: `CRM_DEPLOY_HOST`, `CRM_DEPLOY_USER`, `CRM_DEPLOY_PORT`,
   `CRM_DEPLOY_SSH_KEY`, `CRM_DEPLOY_KNOWN_HOSTS`.
   Variables: `CRM_DEPLOY_PATH`, `CRM_AUTO_DEPLOY_ENABLED=false`.
   Токены бота и `.env` остаются на сервере.
7. После проверки настроек включить `CRM_AUTO_DEPLOY_ENABLED=true`.
   Само изменение переменной обновление не запускает.
8. Отправить согласованную безвредную правку без миграций (например, уточнить
   журнал), дождаться полного CI → Deploy CRM. Не считать `Already installed`
   проверкой переключения: нужен новый коммит относительно серверного HEAD.
9. Проверить `CRM deployment healthy: <SHA>`, совпадение серверного HEAD,
   наличие резервной копии, ответ `/start` и открытие кабинета. Обновить журнал
   фактическим результатом. После завершения настройки `gh auth logout --hostname github.com`.

Если firewall не пускает GitHub runners, не менять его вслепую — выбрать отдельное
решение для CRM. Проверка SSH-ключа сервера строгая (`StrictHostKeyChecking=yes`);
отпечаток берётся на самом сервере, а не доверяется сетевому `ssh-keyscan`.

## Дальнейшая работа и остановки

Обычные согласованные правки, отправленные в рабочую ветку, выкладываются сами
после обоих наборов тестов. Разработчик не должен менять схему в обход
`models.py`/`migrate.py` или смешивать миграцию с обычной выкладкой.
При изменении базы сначала выключить автоматику, сделать проверенную копию,
проверить совместимость старой/новой версии и план возврата, выполнить отдельное
ручное обновление. После проверки снова включить обычную автоматику.

Остановить будущие выкладки: `CRM_AUTO_DEPLOY_ENABLED=false` (Repository variable).
Уже запущенную выкладку это не прерывает. При ошибке не удалять базу и не делать
`git reset --hard`; посмотреть причину в job. Сырые контейнерные логи в CI
не публикуются, чтобы случайно не показать персональные данные или секреты.
