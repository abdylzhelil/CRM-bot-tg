# Архитектура КлиентРадара (на 15.10.2026)

## Общая картина
Один процесс Python (контейнер `crm-bot-tg-bot-1`), внутри — несколько независимых частей на одном asyncio-цикле и одной базе SQLite (`data/crm.db`, режим WAL):

```
Telegram ◄──── бот (aiogram, app/bot) ───────────────┐
                                                     │ общие функции
Telegram-группы ◄─► разведчики (Telethon, app/scout) ┤  app/services/*   ◄── SQLite (WAL)
   (читают заявки, публикуют оплаченную рекламу)     │  (правила, раздача,
Бот модерации ───► приём заявок (app/feed, :8090) ───┤   оплата, CRM, реклама…)
Браузер/Telegram ► кабинет (app/web, :8091) ─────────┤
ЮKassa ◄── ссылки на оплату, опрос статуса ──────────┘
```
Снаружи: Caddy бота модерации (80/443) → `crm.213-148-11-155.sslip.io` → `crm-web:8091`. Внутренний приём заявок `:8090` наружу не открыт. UptimeRobot проверяет `/healthz`.

## Запуск (`app/main.py`)
`init_db` → `upgrade_schema` (новые колонки) → `seed` + `migrate_data` → `build` бота → `manager.start` (разведчики) → фоновые задачи → `setup_profile` → «🟢 Бот запущен» → приём заявок и кабинет → опрос Telegram.

Фоновые задачи (каждая в своём цикле; ошибка → лог + тревога админу не чаще раза в 15 мин, цикл продолжает работу):

| Задача | Частота | Что делает |
|---|---|---|
| `manager.watchdog` | постоянно | переподключает разведчиков |
| `join_loop` / `search_loop` / `rotation_loop` | минуты/часы | вступление в группы (≤10 в день, повторы заявок), поиск, ротация |
| `publish_loop` | 1 мин (после поста 40–120 с) | публикация оплаченной рекламы; раз в ~30 мин — напоминание/автоотмена неоплаченных заказов |
| `delivery_loop` | 20 с | заявки с задержкой и после режима тишины |
| `channel_loop` | минуты | открытые каналы `t.me/s/` |
| `reminder_loop` | 60 с | напоминания CRM, вечерний отчёт |
| `link_loop` | 15 с | статус ссылок ЮKassa → дни тарифа или оплата рекламы |
| `expiry_loop` | 1 ч | конец 💎, автопродление, «возврат ушедших» |
| `stats_loop`, `backup_loop`, `cleanup_loop`, `retention_loop`, `receipts_loop`, `heartbeat_loop` | часы/сутки | канал статистики, копия базы, пустые аккаунты, срок хранения заявок, напоминание про чеки, сторож |

## Слои (как должно быть) и что есть сейчас
1. `models.py`, `db.py`, `migrate.py` — данные. Схему меняем моделями; новые колонки добавляет `migrate.upgrade_schema`.
2. `services/*` — вся логика (не знает про Telegram и HTTP).
3. Входы: `bot/handlers/*` (кнопки/команды), `web/*` (API кабинета), `feed/*` (приём от бота модерации), `scout/*` (чтение и публикация в группах). Входы только вызывают сервисы.
Правило: бот и кабинет делают одно и то же через одни функции (`lead_actions`, `crm`, `profile_edit`, `settings.validate`, `retention`, `users_admin`, `autosetup`, `payments`).

**Долг по слоям:** часть сервисов импортирует `app.bot.notify`/`app.bot.common` (отправка сообщений, кнопки), а `web/api.py` берёт из хендлеров `category_name`, `STATUS`, `ad_card`, `refund_line`, `user_stats`. Работает, но связывает кабинет с aiogram. План: вынести эти функции в `services/`.

## Путь заявки
источник (разведчик / бот в группе / feed / открытый канал) → `services/pipeline` (свои разведчики и наши посты — не заявки; антиспам, дубли, категория, город) → `distribute` (кому и когда: поровну, уровни, лимиты, автор группы первым) → `notify` (карточка) → пользователь: ответить, ✅ в работу (→ `crm`), спам (→ чёрный список), коллеге. Заявки хранятся `lead_keep_days` (90) дней.

## Путь оплаты тарифа
💎 Тариф → `payments.create_link` (цена и пользователь — на сервере) → `pending_links` → `link_loop` опрашивает ЮKassa → `Payment` (уникальный `charge_id`, повтор не засчитывается) → дни тарифа, % пригласившему. Возврат — кнопка у админа (`payments.refund` + снятие дней). Автопродление — `renew_due` (выключено `autorenew`=0).

## Путь рекламы через разведчиков (выключено `adpost_enabled`=0)
```
покупатель: 🌐 Каталог → 📣 Реклама в группах (или ссылка ?start=ads, /ads)
  → текст → выбор групп/каналов (только ads_allowed и с готовым аккаунтом-публикатором)
  → цена = сумма цен групп (на сервере) → ad_orders: pending
админ: ✅ одобрить / ❌ отклонить с причиной / 💰 изменить цену  (или автоодобрение, если нет запрещённых слов)
  → approved → 💳 ссылка ЮKassa (pending_links.order_id) → link_loop → Payment(days=0) + mark_paid → paid
  → ad_posts: queued → publish_loop → аккаунт ad_account_id|account_id пишет в группу → sent/failed
  → все посты разошлись → done, покупателю ссылки на посты
```
Лимиты: на аккаунт `adpost_daily_limit` в сутки и пауза `adpost_gap_min`, на группу `adpost_group_daily` в сутки (сутки — местные, как у заявок). FloodWait/SlowMode → перенос; PeerFlood → аккаунт «limited» + тревога + перенос на сутки; запрет писать → пост failed с причиной (админ может повторить).

## Данные и границы доступа
Каждый пользователь видит только свои заявки (`deliveries`), клиентов (`clients.user_id`) и заказы рекламы. Роли: бесплатный / 💎 / админ определяются по базе на каждый запрос. Кабинет: вход по подписи Telegram, `/api/admin/*` закрыты для не-админов.

## Инварианты (что всегда должно быть правдой — проверяется тестами)
- Деньги: цену и получателя считает сервер; один платёж ЮKassa засчитывается один раз; лишняя/поздняя оплата рекламы не теряется — пишется `Payment` и админ получает кнопку возврата.
- Оплата рекламы — `Payment` с `days=0`: попадает в выручку и в напоминание про чеки; её возврат отменяет заказ и не трогает тариф и карту.
- Посты наших разведчиков (`scout_accounts.tg_user_id`) не становятся заявками.
- Текст рекламы отправляется как есть (без Markdown) и с подписью `adpost_footer`.
- `/deleteme` отменяет открытые заказы рекламы и стирает их тексты; чистка «пустых» аккаунтов не трогает тех, у кого есть оплата или заказ рекламы.
- Одна заявка уходит человеку один раз: `notify.flush_due` идёт под замком и сохраняет «отправлено» после каждой; «подождите» от Telegram (RetryAfter/сеть) — не потеря, заявка уйдёт следующим проходом. На паузе — не шлём; старше суток — не шлём совсем.
- Статусы заказа рекламы меняются одной командой в базе (`adposts._claim`): двойное нажатие ✅ или оплата во время отмены не поставят посты дважды; возврат денег идёт по одному за раз (`payments._refund_lock`).
- Фоновые циклы не останавливаются от одной ошибки базы; выход из пустых групп (`rotation_loop`) считается от отметки в базе (`settings.rotation_at`), а не от перезапуска, и не трогает группы, где продаём рекламу.
- Каждая новая настройка есть в DEFAULTS, LABELS, SHORT, HINTS, SECTIONS (и RANGES/FLAGS для чисел/флагов).

## Надёжность
- SQLite в режиме WAL + `busy_timeout` (запись и чтение не мешают друг другу). Копия базы каждый день (`data/backups`, 7 штук), раз в неделю файлом администратору. **Копировать базу руками при работающем боте нельзя** — только из `data/backups`.
- Ошибки обработчиков и фоновых задач → лог + тревога админу (не чаще раза в 15 минут). «🟢 Бот запущен» при старте. Внешний сторож UptimeRobot.
- CI на GitHub: pytest на каждый push; красный крестик — сервер не обновлять.
- Журнал контейнера ограничен (3 файла по 10 МБ). Память: ~265 МБ бот из 961 МБ сервера; «Состояние бота» предупреждает при <200 МБ.

## Риски (осознанные, на владельце)
- **Блокировка разведчика** за рекламу (PeerFlood/жалобы): начинать с малых лимитов, рекламу — только в группах, где админ разрешил. Заблокированный аккаунт перестаёт и искать заявки.
- **Маркировка рекламы (erid)** по ФЗ «О рекламе» — `adpost_footer` нужно дополнять вручную.
- **Каналы:** публиковать может только аккаунт, который владелец канала сделал админом с правом постов.
- Бот модерации в группе может удалить рекламный пост как спам — разрешать рекламу в своих группах с этим учётом.
- Рекламодатели считаются «настроенными» в воронке (у них нет ниш, заявок они не получают).
- Нажатие «💳 Оплатить» несколько раз создаёт несколько ссылок; если оплатят две — вторая придёт как «лишняя оплата» с кнопкой возврата.
- `/deleteme` во время открытой оплаты удаляет ссылку: если человек всё же заплатит — деньги вернуть вручную через ЮKassa.

## Возврат и исправление (правило интерфейса)
- Заявки: списки по статусам в боте (📥 Заявки → 🆕/⏰/✅/❌/🚫 с числами, `ll:<статус>:<страница>`), «↩️ Вернуть в новые» после Отказа/Спама/Отложить (`lead_actions.restore`: для спама снимается свой голос и, если голосов стало меньше порога, — запись чёрного списка); в кабинете вкладка «Спам» и та же кнопка (`POST /api/leads/{id}/restore`).
- Группы пользователей: админ — «❌ Отклонённые» в 📝 От пользователей и «↩️ Всё-таки одобрить» (`up:rej`, `up:rok`); пользователь — в 📂 Мои группы видны черновики и отклонённые: «✏️ Дозаполнить» / «🔄 Подать снова» (`cg:resume`) и «🗑» (`cg:drop`, группа освобождается).
- Клиенты CRM: «✏️ Имя», «🔕 Без напоминания», «🗑 Удалить» с подтверждением (бот `cl:name/unrem/del/delok`; кабинет PATCH `name`/`remind_off`, `DELETE /api/clients/{id}`; `crm.cancel_reminders/delete_client/display_name`).
- Спам-тексты (`spam_samples`, `services/spamtexts.py`): «🚫 Спам» от админа или N голосов запоминает текст — похожий с любого аккаунта отсеивается в `pipeline.process`; 🛡 → «🧩 Спам-тексты» (удалить/добавить). Возврат заявки из спама удаляет её образец.
- Чёрный и белый списки: все записи страницами по 10, поиск по ID/@нику, карточка с причиной; «♻️ Убрать» снимает и голоса «спам» (иначе один новый голос вернул бы автора).

## Ограничения
- Один процесс и одна база: всё падает и перезапускается вместе (Docker поднимает сам). Для текущего размера это нормально.
- Состояние диалогов (`MemoryStorage`) хранится в памяти: при перезапуске незаконченный ввод сбрасывается.
- Лимит запросов кабинета и кулдаун тревог — в памяти процесса.
- SQLite рассчитана на сотни/первые тысячи активных людей; при росте — PostgreSQL.

## Узкие места роста
- `services/catalog.browse` и `levels.rating` читают все группы каталога и для каждой ищут корень категории (N+1): заметно при сотнях групп.
- Раздача заявок для каждого кандидата считает нагрузку за сутки и минус-слова отдельными запросами — при тысячах пользователей в одной нише собрать одним запросом.
- `cleanup.empty_users` — по 4 запроса на каждого незарегистрированного (их немного).
