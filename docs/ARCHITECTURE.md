# Архитектура КлиентРадара (на 14.10.2026)

## Общая картина
Один процесс Python (контейнер `crm-bot-tg-bot-1`), внутри — несколько независимых частей на одном asyncio-цикле и одной базе SQLite (`data/crm.db`, режим WAL):

```
Telegram ◄──── бот (aiogram, app/bot) ───────────────┐
                                                     │ общие функции
Telegram-группы ◄─ разведчик (Telethon, app/scout) ──┤  app/services/*   ◄── SQLite (WAL)
Бот модерации ───► приём заявок (app/feed, :8090) ───┤  (правила, раздача,
Браузер/Telegram ► кабинет (app/web, :8091) ─────────┘   оплата, CRM, …)
фоновые задачи (app/main.py): раздача заявок, напоминания, бэкап, чистка, хранение заявок, оплата по ссылкам, сторож
```
Снаружи: Caddy бота модерации (80/443) → `crm.213-148-11-155.sslip.io` → `crm-web:8091`. Внутренний приём заявок `:8090` наружу не открыт. UptimeRobot проверяет `/healthz`.

## Слои (как должно быть) и что есть сейчас
1. `models.py`, `db.py`, `migrate.py` — данные. Схему меняем моделями; новые колонки добавляет `migrate.upgrade_schema`.
2. `services/*` — вся логика (не знает про Telegram и HTTP).
3. Входы: `bot/handlers/*` (кнопки/команды), `web/*` (API кабинета), `feed/*` (приём от бота модерации), `scout/*` (чтение групп). Входы только вызывают сервисы.
Правило: бот и кабинет делают одно и то же через одни функции (`lead_actions`, `crm`, `profile_edit`, `settings.validate`, `retention`, `users_admin`, `autosetup`).

**Долг по слоям:** часть сервисов импортирует `app.bot.notify` (отправка сообщений), а `web/api.py` берёт из хендлеров `category_name`, `STATUS`, `ad_card`, `refund_line`, `user_stats`. Работает, но связывает кабинет с aiogram. План: вынести эти функции в `services/` (небольшой рефакторинг).

## Путь заявки
источник (разведчик / бот в группе / feed / открытый канал) → `services/intake` (антиспам, дубли, категория, город) → `distribute` (кому и когда: поровну, уровни, лимиты) → `notify` (карточка) → пользователь: ответить, ✅ в работу (→ `crm`), спам (→ чёрный список), коллеге. Заявки хранятся `lead_keep_days` (90) дней.

## Данные и границы доступа
Каждый пользователь видит только свои заявки (`deliveries`) и клиентов (`clients.user_id`). Роли: бесплатный / 💎 / админ определяются по базе на каждый запрос. Кабинет: вход по подписи Telegram, `/api/admin/*` закрыты для не-админов. Деньги: цены и пользователь берутся на сервере.

## Надёжность
- SQLite в режиме WAL + `busy_timeout` (запись и чтение не мешают друг другу). Копия базы каждый день (`data/backups`, 7 штук), раз в неделю файлом администратору в Telegram. **Копировать базу руками при работающем боте нельзя** — только из `data/backups`.
- Ошибки обработчиков и фоновых задач → лог + тревога админу (не чаще раза в 15 минут). «🟢 Бот запущен» при старте. Внешний сторож UptimeRobot.
- Журнал контейнера ограничен (3 файла по 10 МБ).
- Память: ~265 МБ бот из 961 МБ сервера; `Состояние бота` предупреждает при <200 МБ.

## Ограничения (осознанные)
- Один процесс и одна база: всё падает и перезапускается вместе (Docker поднимает сам). Для текущего размера это нормально.
- Состояние диалогов (`MemoryStorage`) хранится в памяти: при перезапуске незаконченный ввод сбрасывается.
- Лимит запросов кабинета считается в памяти процесса.
- SQLite рассчитана на сотни/первые тысячи активных людей; при росте — PostgreSQL (в `docker-compose.yml` описан переход).

## Узкие места роста (смотреть при росте числа групп/людей)
- `services/catalog.browse` и `levels.rating` читают все группы каталога в память и для каждой делают запрос корня категории (N+1): заметно при сотнях групп.
- Списки заявок/клиентов в кабинете для каждой строки узнают название категории отдельным запросом (до 20 за страницу — терпимо).
- Раздача заявок считает нагрузку по суткам на каждую заявку.
